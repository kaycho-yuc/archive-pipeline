# A reused helper's fallback branch can reintroduce the exact bug it's meant to avoid

**Problem (one line):** Migrating 192 notes to the new detect-or-미정 policy needed to reuse `migrate_revise_notes.py:_body()`'s body-extraction technique, but that function's own fallback (return full text, including frontmatter, when `## 원문` is missing/short) would reopen the circularity bug the previous session had just fixed — plus a naive `--redetect` default would silently overwrite every human decision made through `review_pending.py`.

## Approach (plain steps)
1. Read the four named files first (`migrate_add_project.py`, `review_pending.py`, `classify.detect_project`, `write_note.UNKNOWN_PROJECT`) before writing anything — the spec referenced exact line-level behavior (`detect_project(source_name, text)`, `## 원문` split) that only makes sense after seeing the real signatures.
2. Copied `_body()`'s *technique* (split on `## 원문`, require ≥30 chars) but not its *fallback*: on missing/short section it returns `""` instead of the full text. The spec's CRITICAL note explained why — frontmatter contains `project: 성수동 리모델링`, and that string is itself a registered identifier, so any full-text fallback reopens the exact circular measurement the prior session (see `2026-08-02-silent-default-fakes-metadata-completeness.md`) had already diagnosed and fixed. A test (`test_redetect_does_not_scan_full_text_for_circularity`) asserts the guard directly: a note whose frontmatter carries the label but whose body/filename don't would fail if full text were scanned.
3. Kept `--redetect` an explicit opt-in, not the new default, because a note that already went through `review_pending.py` typically has *no* matching identifier in its own text — that is precisely why it was pending. A default that re-derives on every run would quietly demote every human decision back to 미정. Put the reasoning in a comment on the flag itself, not buried in a docstring.
4. Fixed a second, unrelated bug found while reading `review_pending.py`: it imports `_backup` from `migrate_add_project` but has its own `VAULT`. Since `_backup()` read the *module-global* `VAULT`, monkeypatching `review_pending.VAULT` in a test wouldn't redirect the backup — it would zip the real vault. Gave `_backup` an optional `vault` parameter and made `review_pending.py` pass its own.
5. Ran the dry run (`--redetect`, no `--execute`) against the real vault as the actual verification, not just the test suite. It reported 28 changes — the expected count — but read every line instead of trusting the count: 27 were `'성수동 리모델링' → '미정'` as predicted, one was `'기타' → '미정'` (an unrelated personal dev-notes file that happened to have `domain: 업무`). The spec said "if the number differs, STOP and report" — the count matched but the *content* of one entry didn't fit the stated invariant, so it was reported as a discrepancy rather than silently accepted or worked around.

## Judgment calls (what was NOT done, and why)
- Did **not** reuse `_body()` verbatim by importing it. A function named identically that behaves differently on the fallback path is more dangerous than a small local copy with a CRITICAL comment explaining the divergence — copying it silently would have looked like "did what was asked" while quietly reopening a bug the task explicitly warned against.
- Did **not** make `--redetect` scan for and preserve project values that were "probably manually confirmed." No such marker exists in the frontmatter; guessing would be exactly the kind of unrequested heuristic the task warned against. The flag stays blunt and opt-in instead.
- Did **not** edit the anomalous `'기타' → '미정'` note, adjust the test corpus, or otherwise touch anything to make the dry-run output match "all 28 are 성수동 리모델링 → 미정." The task was explicit that forcing the number is worse than an honest mismatch report.
- Did **not** run anything with `--execute`. Verification was dry-run only, and the zip check confirmed no new `vault_backup_*.zip` was created by the run (only a pre-existing one from a prior session, dated before this session started).

## Reusable rule
**When told to reuse another function's technique, check its fallback branch against your own safety invariant before importing it — a shared name does not guarantee shared safety.** If the fallback conflicts with the invariant the task is protecting, copy the logic locally with a comment explaining exactly why it diverges, so nobody "simplifies" it back into the shared function later.

**A verification step that only checks a count can pass while the content is wrong.** When a spec states an invariant ("all N changes are X → Y"), check every row against it, not just `len(rows) == N` — and report a content mismatch exactly like a count mismatch: stop, show the actual list, don't adjust anything to force agreement.
